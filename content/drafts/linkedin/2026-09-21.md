## Option 1

Last week I launched a paid tier for the Purplelink Daily Digest.

The decision to build it came from a simple comparison. Paper Review, my automated paper review tool, had zero orders in the trailing 30 days. The Digest page was the fourth-highest-traffic page on the site. The Digest had proven demand; Paper Review had potential demand. I built where people were already showing up.

The tier structure is straightforward. Paid subscribers ($5/month or $40/year) get same-day email delivery. New free subscribers get a two-day delay. Everyone who was subscribed before the paid tier launched gets grandfathered onto same-day delivery regardless of tier.

For billing management I used Stripe's Customer Portal rather than building a custom account system. It handles plan upgrades, cancellations, and payment method updates without any extra code on my side. The tradeoff is some loss of visual consistency, but for a subscription product at this stage the faster launch is worth it.

I also cut per-subscriber personalization from version one. The paid curation newsletters I looked at almost all send one edition to everyone. The value comes from editorial judgment, not targeting. And running the curation pipeline once per subscriber would have multiplied the backend cost with every new signup.

The paid tier is live. Whether fourth-place organic traffic converts to subscriptions is something I will find out over the next few weeks.

## Option 2

The citation generator on purplelink.llc had been silently failing for arXiv papers. Type in an arXiv ID, get nothing back.

The first thing I diagnosed was a Content Security Policy gap. My browser security headers were blocking fetches to arXiv's export domain because it was not in the allowlist. I added it. Still zero results.

The second problem was different. arXiv's export API does not send an Access-Control-Allow-Origin response header. Crossref and Open Library both send it, which is why those work fine when the citation generator calls them directly from the browser. arXiv does not. When a browser makes a cross-origin fetch and the server does not include that header in the response, the browser rejects the response regardless of what your own security policy allows. CSP and CORS are two separate gates. I had cleared mine. arXiv had not cleared theirs.

The fix was a server-side proxy: a Netlify serverless function that accepts an arXiv ID, fetches arXiv's API from the server side where cross-origin restrictions do not apply, and returns the same XML to the browser unchanged. The client-side parsing code did not need to change at all.

The citation generator now handles arXiv IDs alongside DOIs and ISBNs. If you tried to look up an arXiv paper there before and got nothing back, it should work now.

## Option 3

Last week I fixed two bugs in the citation generator that had been hiding behind the same symptom.

Both returned zero results. No error message, just nothing. When two different broken things produce identical output, it is easy to assume they are one problem. They were not.

The first bug was a missing entry in my browser security policy. Fetches to arXiv's export domain were being blocked because that domain was not in the allowlist. That was straightforward to fix.

With that cleared, the result was still zero. The second bug was deeper. arXiv's export API does not send the header that browsers require for cross-origin requests. Crossref and Open Library both send it. arXiv does not. Fixing my own policy revealed the second constraint rather than resolving the symptom. The actual fix was a server-side proxy function that fetches arXiv from the server and forwards the response to the browser, bypassing the cross-origin restriction entirely.

One symptom, two root causes, two different types of fixes.

The debugging process is written up in more detail on the Purplelink blog. If you have run into a situation where fixing one thing just made a different problem visible, that post might be useful.

## Selected
Option 1 -- it is the most concrete product decision story in this batch, uses specific real data (zero orders versus fourth-place traffic), shows honest prioritization based on actual demand rather than wishful thinking, and ends with a genuinely open question rather than a manufactured hook.

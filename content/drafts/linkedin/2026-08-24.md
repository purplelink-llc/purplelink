## Option 1

For three months, the Purplelink stats endpoint read event blobs one at a time. Each page view is stored as a separate JSON object in object storage. To compute totals, the function fetched a day's event listing, then awaited each blob read sequentially. The code had a comment: "fine at early-stage volume."

At 670 events over 30 days, wall-clock time hit 21 seconds. The function timeout is 10 seconds. The dashboard fell back to stale figures.

The failure arrived through individual latency rather than the traffic spike I expected. Nothing dramatic on any single blob read. Just 670 of them, each slightly slower than expected, stacking up.

The fix is bounded concurrency: 10 day listings in flight at a time, 64 event reads. Not an unconstrained Promise.all, because the number of events is unbounded in principle and dispatching them all at once trades a slow response for a flaky one. Bounded concurrency, preserved order, counting logic untouched.

The actual long-term fix is pre-aggregated counters: compute totals incrementally as events arrive. The parallel version buys time to build that deliberately.

The lesson I keep relearning: writing "this will break" in a comment is not the same as scheduling when to fix it.

## Option 2

When I built BibTeX Builder, the obvious approach would have been to scrape journal pages or Google Scholar for citation data. I did not do that. Scraping is fragile, and most academic publishers prohibit it explicitly.

CrossRef has a content-negotiation endpoint that returns formatted BibTeX directly. You send a GET request with the DOI and an Accept: text/x-bibtex header, and CrossRef returns an @article, @inproceedings, or @book entry, typed by the publisher. The metadata is authoritative: it comes from the same registry publishers use to assign DOIs.

arXiv has its own Atom API. The tool queries that, parses the XML, and formats an @misc entry with the eprint, archivePrefix, and primaryClass fields that most LaTeX journal style files expect for preprints.

The practical result: paste a list of DOIs and arXiv IDs, one per line, get a .bib file in a few seconds. Entries that fail to resolve appear in a separate list so you know exactly which ones to check manually. Nothing is retained on the server after the response is sent.

I published a guide this week walking through the full workflow, including how to spot-check entries after download and how to validate the file before submitting a manuscript.

Tool: purplelink.llc/tools/bib-builder/ and guide: purplelink.llc/guides/build-bibtex-from-dois/

## Option 3

I published a guide this week on producing diff PDFs for journal resubmissions and want to explain one deliberate gap in the tool it covers.

The LaTeX Diff tool takes two .tex files or .zip archives and returns a compiled PDF showing additions underlined and deletions struck through. Word-level diffing, browser-based, no local Perl or LaTeX installation needed.

The tool does not diff the contents of tabular environments. This is intentional.

latexdiff's default behavior marks changes inside tables with inline annotation markup placed within cells. That markup corrupts column alignment. The compiled output is either visually broken or fails to compile entirely. The fix that works reliably is treating each table as an opaque block: show the new version, skip the diff. Reviewers can compare table changes manually.

I document this explicitly in the guide because researchers relying on diff PDFs for revision planning will notice the gap immediately if a table changed and nothing shows up. Knowing the reason before you encounter it is more useful than discovering it mid-submission.

Tool: purplelink.llc/tools/latex-diff/ and guide: purplelink.llc/blog/producing-a-diff-pdf-for-journal-resubmission/

## Selected

Option 3 -- it is the most directly useful to the academic researcher audience, explains a specific and honest design decision (deliberately omitting table diffing because latexdiff's inline markup corrupts column alignment), and helps researchers avoid a confusing surprise at a high-pressure moment in their revision workflow.

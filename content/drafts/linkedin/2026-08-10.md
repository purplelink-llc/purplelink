## Option 1

For over a week the Purplelink dashboard reported zero conversions. No purchases, no sign-ups. I assumed traffic was slow.

It was not slow. The measurement was wrong.

All tool purchase tracking runs through a wrapper around the analytics beacon. When someone buys a Paper Review or pays for a response letter check, that event touches the backend and gets counted. Waitlist sign-ups are different. They go through Netlify Forms, a hosted form service completely outside the beacon. From the dashboard's perspective they did not exist.

When I wired in waitlist tracking this week I found five ModernTex sign-ups from the previous two weeks. The only non-zero conversion across either Purplelink site had been happening without appearing anywhere in the reporting.

The underlying problem: what a dashboard measures is determined by how your infrastructure is wired, not by what users are actually doing. If the two are misaligned you will read silence as a signal when it is just a gap. I now treat any new form or checkout flow as requiring a metric check at launch, not after the fact.

ModernTex is a LaTeX editor I am building for researchers who write long documents. The waitlist is at purplelink.llc/moderntex/

## Option 2

Resubmitting a manuscript means producing two documents: the revised text and the response letter. Most rounds go wrong at the response letter.

The specific failure mode has a name: hand-waving. The response letter acknowledges a reviewer concern without actually fixing the underlying issue. From the author's side it reads as complete. From the reviewer's side it is obvious. A hand-waved response can stall a revision that was otherwise ready to accept.

The Response to Reviewers tool at Purplelink runs a three-persona check on your draft letter. A Skeptical Reviewer reads each paired reviewer comment and response, checking whether the response actually addresses the concern. A Tone Editor looks for defensive or dismissive phrasing. An Editor-in-Chief estimates whether the overall letter would survive another round. Each reviewer comment gets a verdict: addressed, partially addressed, hand-waved, rejected with argument, or not evaluable.

This week I published a step-by-step guide for the full workflow. One detail that matters: the report is deleted from the server the moment you retrieve it. It cannot be recovered after that. Copy or download before closing the tab.

The tool is $6. The guide is free.

## Option 3

The citation generator on Purplelink was silently broken for at least a week. I did not catch it until I ran through all the tools deliberately.

The tool calls the Crossref API to resolve DOIs and Open Library to look up ISBNs, both directly from the browser. Every call was returning "Network error." Not a server problem. A Content-Security-Policy directive was blocking the browser from connecting to those domains.

Purplelink runs a strict CSP. Every external origin the site connects to must be listed explicitly in the header. That is deliberate: the policy limits what a compromised dependency or injected script could contact. It works well until a new tool makes a browser-side API call and the domain is not in connect-src. The browser enforces this silently. The server never sees a failure. The user sees "Network error."

Adding api.crossref.org and openlibrary.org to the policy fixed DOI and ISBN lookups. The arXiv lookup path is still broken for a different reason. The arXiv export endpoint returns no CORS header, so a browser request cannot read the response regardless of what CSP allows. That path will route through the backend, which already handles arXiv server-side for the BibTeX builder.

Any new browser-side API call needs two things checked at the same time: CORS headers on the destination, and connect-src in the CSP. Forgetting either looks identical to the user.

The citation generator is at purplelink.llc/tools/citation-generator/

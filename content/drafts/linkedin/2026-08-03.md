## Option 1

Seven of the Purplelink tools call a backend server. The instrumentation for usage tracking lives in a wrapper around that fetch call, so every backend tool gets counted automatically. Two tools were invisible: the citation generator and the LaTeX table generator. Both run entirely in the browser. No server call, nothing to intercept. From the stats dashboard, they looked identical to any other page load.

Fixing the tracking was straightforward. Deciding what to count was not.

For the citation generator, the answer came from how the tool works. It has two entry points: DOI lookup and manual entry form. Submitting either is a deliberate action. Two lookups count as two runs, the same way two backend requests would.

For the LaTeX table generator, the tool regenerates output on every keystroke. Counting each regeneration would mean counting typing. A single editing session might produce 50 events. What I actually wanted to measure was whether someone got useful output. So it counts once per visit, the first time real content appears in the output field.

The underlying question is what the metric is for. For the citation generator: output volume, how many citations were generated. For the table generator: adoption, how many people used it and got something out of it. The right definition of a run follows from that question, not from how the code is built.

I wrote this up at purplelink.llc/blog/what-counts-as-a-run/

## Option 2

The most consistent peer review rejection note I see on academic manuscripts is some version of: the authors have not engaged with relevant prior work. Most of the time, the authors have engaged with it. They missed one paper the reviewer expected.

I built a tool called Citation Gap Analysis to catch that problem before submission. It takes a PDF of your manuscript, reads the full text and bibliography together, and flags the prior-art omissions a reviewer would likely notice: foundational method references, near-identical prior findings, missing dataset attributions. Each suggestion includes the section of the manuscript where the reference belongs and a reason the reviewer would notice the absence.

This week I published a step-by-step guide for running it before you submit, because the workflow has a few specifics worth knowing. The most important one: download the result before you close the tab. The report is deleted from Purplelink's servers the moment it renders. Your manuscript PDF goes to Anthropic's Claude API for the scan and is not retained after the result is returned. That data policy is stated in the guide, not buried.

The tool is $3 per scan. The guide is free.

## Option 3

Purplelink has two citation tools that are easy to confuse, and they do opposite things.

The BibTeX Validator checks the citations you already have. Give it a .bib file and it verifies that entries are correctly formatted, DOIs resolve, required fields are present, and the structure will not cause LaTeX errors. It runs in the browser, costs nothing, and the problem it solves is accuracy.

Citation Gap Analysis runs the other direction. Give it your full manuscript PDF and it flags citations you probably should have but do not: foundational papers in your method that experts assume will be cited, near-identical prior findings you should differentiate against, dataset references you built on without attribution. Each suggestion includes a reason, so you can judge relevance without evaluating candidates cold. It costs $3 per scan and the problem it solves is completeness.

I built the Validator first because broken BibTeX entries are a verifiable, specific problem. Citation Gap came later because reviewers kept flagging missing prior art, which is a different problem with a different tool shape. One belongs before you compile. The other belongs before you submit.

I try to be explicit about this distinction in the UI because reaching for the wrong tool at the wrong stage wastes time.

Both are at purplelink.llc/tools/
